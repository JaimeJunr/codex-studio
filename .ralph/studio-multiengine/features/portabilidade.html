Portabilidade e setup honesto

Feature Overview

Fechar a distância entre o que o README promete e o que a máquina de um terceiro consegue executar. Três coisas concretas: um diagnóstico que diz o que falta em vez de falhar em silêncio; resolução de caminhos que não assume Linux nem assume o PATH de um shell interativo; e o alinhamento entre o mecanismo documentado e o mecanismo que de fato funciona.

O ponto de partida não é teórico. Medido em 2026-09-13 na máquina do autor: CURSOR_MCP_BRIDGE_DIST — a variável que o .mcp.json:5 do codex-image interpola — está vazia, e mesmo assim tudo funciona, porque o que funciona é um MCP global configurado por fora do repo. O caminho descrito no README nunca foi exercitado de ponta a ponta, nem aqui.

User Stories

US-005 Blocked · US-004, US-006 plugin motor

Como usuário numa máquina nova, quero rodar um diagnóstico que liste o que está presente e o que falta, para saber o que instalar sem precisar perguntar a ninguém.

  • AC: Existe um script Python no plugin motor exposto como slash command, seguindo o padrão que o repo já usa (spritekit.py + commands/setup.md, onde o command resolve o ${CLAUDE_PLUGIN_ROOT}).
  • AC: O diagnóstico cobre, cada um com veredito presente/ausente: o MCP do bridge, motor Codex, motor Grok, Aseprite, Pillow, python-pptx e o pixel-plugin.
  • AC: Cada item ausente vem com o comando ou passo exato que resolve — nunca só "não encontrado".
  • AC: O diagnóstico nomeia a versão esperada do polyagent-mcp em vez de assumir qualquer uma, e distingue "bridge ausente" de "bridge presente em versão incompatível".
  • AC: Rodar o diagnóstico não gera imagem, não faz chamada de rede e não escreve nada fora do config do projeto.
  • AC: O diagnóstico reutiliza o mesmo critério de disponibilidade definido em multi-engine — a definição nasce lá e é consumida aqui, sem uma segunda versão da regra.
US-006 Ready spritekit.py + plugin motor

Como usuário de macOS ou Windows, quero que caminhos e binários sejam resolvidos pela convenção do meu sistema, para não depender de um layout que só existe em Linux.

  • AC: Existe um único diretório de config do projeto, resolvido por SO: XDG no Linux, ~/Library/Application Support no macOS, %APPDATA% no Windows.
  • AC: Um ~/.config/codex-sprite/config.json preexistente é migrado para o novo local, sem perda de configuração e sem exigir ação do usuário.
  • AC: A resolução de binário (motores e Aseprite) segue a cadeia já provada no spritekit.py:285-305: env var → config → PATH → locais conhecidos de instalação. Um binário instalado fora do PATH herdado — como o ~/.grok/bin/grok medido em 2026-09-13 — é encontrado.
  • AC: Nenhum path POSIX hardcoded e nenhum shell-ismo no código Python; caminhos via pathlib.
  • AC: A auto-detecção do Aseprite via Steam cobre os três layouts de biblioteca (Linux, macOS, Windows), mantendo o setup --path como saída para biblioteca em disco custom.
US-007 Ready codex-image + docs

Como usuário seguindo o README, quero que o caminho documentado seja o caminho que de fato funciona, para não montar uma instalação que nunca foi testada.

  • AC: O MCP global polyagent-mcp passa a ser o caminho oficial e documentado de instalação; o .mcp.json próprio do codex-image, que dependia de CURSOR_MCP_BRIDGE_DIST, deixa de ser o mecanismo declarado.
  • AC: As 47 ocorrências do nome antigo do bridge — 30 linhas em 8 arquivos (medido em 2026-09-14 com a regex do AC seguinte) — generate/SKILL.md, edit/SKILL.md, .mcp.json, codex-image/README.md, plugin.json, marketplace.json, CLAUDE.md, README.md — são alinhadas para polyagent-mcp e o prefixo POLYAGENT_*.
  • AC: Uma varredura por cursor-?(mcp-)?bridge|CURSOR_(MCP_)?BRIDGE no repo retorna vazia, exceto menções deliberadas de histórico no CHANGELOG. A regex precisa cobrir o nome isolado do server (cursor-bridge) — é a chave que o Claude Code usa para resolver o MCP em .mcp.json:3, e uma varredura só pelo nome completo a deixaria viva.
  • AC: A convenção keyless permanece intacta: nenhuma das edições introduz caminho com OPENAI_API_KEY.
US-008 Blocked · US-003 skills downstream

Como usuário sem nenhuma assinatura — ou com assinatura e sem vontade de gastá-la — quero usar o projeto inteiro em modo prompt, para receber o prompt pronto e colar onde eu quiser.

  • AC: O modo prompt vale para toda a superfície do projeto, não só para codex-image: deck, social, infográfico e a família sprite entregam prompt pronto quando pedido.
  • AC: O modo é documentado como escolha legítima, lado a lado com os motores — não aparece na documentação como fallback de erro.
  • AC: Num deck, o modo prompt entrega um prompt por slide, preservando a nomeação numérica que o build_pptx.py exige; o usuário consegue montar o .pptx depois de gerar as imagens por fora.
  • AC: Sem nenhum motor disponível, nenhuma skill do projeto termina em erro sem saída — todas oferecem o prompt.
US-009 Blocked · US-005, US-007 docs

Como pessoa que acabou de achar o projeto, quero um README que me leve do clone à primeira imagem, para não depender de conhecimento que só o autor tem.

  • AC: O README documenta a instalação do zero em passos ordenados, terminando no diagnóstico da US-005 como verificação.
  • AC: Os pré-requisitos externos (polyagent-mcp, motores, Aseprite, pacotes Python) aparecem com o que cada um habilita e o que deixa de funcionar sem ele — o usuário decide o que instalar.
  • AC: O README declara explicitamente que dá para usar o projeto sem nenhum motor, via modo prompt.
  • AC: Validado numa máquina Linux limpa (container ou VM sem o ambiente do autor) por alguém que segue só o texto. macOS e Windows ficam por construção — ver o Assumption Lock do épico.
US-010 Blocked · US-006 scripts + skills

Como usuário que esbarrou numa dependência ausente no meio do trabalho, quero uma mensagem que nomeie o que falta e o comando que resolve, para não precisar abrir o código.

  • AC: O padrão que os scripts já acertaram ("Falta Pillow. Rode: pip install Pillow" em spritekit.py:46; o equivalente para python-pptx em build_pptx.py:21-25) é estendido aos pontos que hoje falham calados: bridge ausente, motor sem credencial, pixel-plugin não instalado.
  • AC: Nenhum ponto de dependência externa termina em stack trace cru ou em silêncio.
  • AC: A mensagem diz o que aquela ação precisava, não só o que falta no geral — o usuário entende por que parou ali.

Functional Requirements

  1. O diagnóstico é o ponto único de verdade sobre o estado do ambiente; nenhuma skill reimplementa a verificação.
  2. Toda resolução de caminho passa pela cadeia env → config → PATH → locais conhecidos, nunca só pelo PATH herdado.
  3. Existe um único diretório de config do projeto, com localização decidida pelo SO.
  4. Toda dependência externa ausente produz mensagem acionável no momento do uso, além de aparecer no diagnóstico.

Scope

Technical Considerations

i

O repo já tem o padrão certo para isto — ele só não foi aplicado de forma uniforme. O spritekit.py resolve o Aseprite por env → config → PATH → auto-detect e absorve falha (spritekit.py:285-305); os scripts dão mensagem de dependência acionável (build_pptx.py:21-25). O que falta é estender isso aos motores e ao bridge, que hoje não têm verificação alguma. Não inventar um segundo padrão: generalizar o que já existe.

O pixel-plugin é dependência opcional e externa, instalada ao lado do projeto. O diagnóstico o reporta como ausente-mas-opcional, e sua ausência não degrada nada além da camada 3 (edição/animação) — o fallback textual para walkgen já existe em handoff/SKILL.md:24 e permanece.

  • Feature 3 — depende desta: o README e o config dir criados aqui carregam o nome novo, então o rename vem depois.

Acceptance Criteria (feature)

Numa máquina Linux limpa, sem nada do ambiente do autor: clonar, seguir o README, rodar o diagnóstico e confirmar que ele lista corretamente cada item como presente ou ausente, com remédio para os ausentes. Instalar apenas um motor e confirmar que o diagnóstico muda de veredito só naquele item. Mover o binário do Grok para um diretório fora do PATH e confirmar que a resolução ainda o encontra pela cadeia de fallback. Com um ~/.config/codex-sprite/config.json preexistente, rodar o projeto e confirmar que a configuração foi migrada sem perda. Sem nenhum motor, gerar um deck e confirmar que sai um prompt por slide, sem erro. Por fim, varrer o repo por cursor-?(mcp-)?bridge|CURSOR_(MCP_)?BRIDGE e confirmar que só sobram menções históricas deliberadas.
