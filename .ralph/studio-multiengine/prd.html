Studio multi-engine, portátil e achável

Tirar o projeto da condição de "funciona na máquina do autor, com um motor só, e ninguém acha" — sem perder o que ele é.

C

Contexto

O projeto é hoje um marketplace de 11 plugins declarativos para Claude Code que faz geração visual keyless — imagens, decks, criativos sociais, infográficos e sprites — roteando pela assinatura do usuário através do polyagent-mcp, nunca por OPENAI_API_KEY. Essa identidade não está em questão e não muda.

O que está em questão é a distância entre o que o projeto é e o que ele consegue entregar a um terceiro. Três lacunas concretas, levantadas no mapeamento do repo: o motor não sabe que existem dois motores; a instalação assume um ambiente que só existe na máquina do autor; e o nome amarra o projeto a um único fornecedor e não é encontrável.

Personas / Actors

Autor/mantenedor — conhece o setup de cor; hoje é o único que consegue rodar tudo Usuário novo — clona do GitHub numa máquina limpa, com ou sem assinaturas Usuário sem motor — quer o prompt pronto pra colar no chat, por escolha ou por falta de assinatura Skill downstream — consome o motor de imagem e precisa pedir o motor certo
R

Requisitos

Feature Index

  1. Multi-engine consciente — Must — o motor de imagem passa a conhecer, declarar e rotear entre Codex e Grok, com fonte única de regra. US-001 a US-004.
  2. Portabilidade e setup honesto — Must — roda numa máquina limpa nos três SOs, diz o que falta em vez de falhar em silêncio, e trata prompt-only como modo de primeira classe. US-005 a US-010.
  3. Rename e descoberta — Should — nome novo que não amarra a fornecedor, rename total sem alias, e descrições escritas pra ser achado no Google e no GitHub. US-011 a US-013.

Ordem de execução

I

Impacto esperado

Problem & Goals

  • O motor é cego aos motores. O parâmetro engine existe no generate_image do bridge mas não é declarado em nenhuma das duas skills de codex-image (generate/SKILL.md:35, edit/SKILL.md:30). A escolha Grok×Codex vive como prosa em quatro lugares downstream que podem divergir entre si. Meta: uma fonte única de regra, consultável, com override explícito.
  • A instalação não é reproduzível. CURSOR_MCP_BRIDGE_DIST é interpolado cru em codex-image/.mcp.json:5 sem verificação alguma: se a variável não existe, o MCP não sobe e nada explica o porquê. O login do Codex nunca é checado. Meta: um terceiro clona, roda um diagnóstico, e o diagnóstico diz exatamente o que falta e como resolver.
  • Prompt-only é tratado como falha. Hoje a degradação para "cole no chatgpt.com/images" só acontece quando algo quebra. Meta: virar escolha deliberada do usuário, disponível mesmo com motor instalado.
  • O upstream já fez o mesmo movimento. O bridge deixou de se chamar pelo nome de um fornecedor (cursor) e passou a se chamar pelo que faz (polyagent) — exatamente o argumento da feature 3 aplicado um nível abaixo. Isso torna manter codex-studio mais incoerente ainda: o projeto se nomearia por um motor que nem seu próprio roteador nomeia mais.
  • O nome esconde o projeto. codex-studio amarra a identidade a um fornecedor que já não é o único motor, e não é um termo que alguém busque. Meta: nome novo e descrições que façam o projeto ser encontrado por quem procura o problema que ele resolve.

Non-Goals

Adicionar um terceiro motor além de Codex e Grok Suporte a OPENAI_API_KEY ou qualquer via com chave Reimplementar as ~50 tools do pixel-plugin dentro do spritekit Distribuição via npm ou registry próprio Alias de compatibilidade para os IDs antigos codex-* Mudar a arquitetura de 3 camadas de plugins

Success Metrics

  • Um terceiro, numa máquina Linux limpa, sai do git clone a uma imagem gerada seguindo só o README — sem perguntar nada ao autor.
  • Nenhuma skill decide motor por conta própria: toda escolha rastreia até a fonte única de regra.
  • Toda dependência ausente produz uma mensagem que nomeia o que falta e o comando que resolve — zero falha silenciosa.
  • Busca pelo problema ("keyless image generation claude code", "pixel art plugin claude code") retorna o repositório na primeira página.

Alinhamento

High-Level Risks & Dependencies

!
  • macOS e Windows sem validação real — não há máquina para testar. Mitigação: portabilidade por construção (pathlib, zero path POSIX hardcoded, zero shell-ismo) + revisão contra checklist; o AC declara Linux validado e os outros dois por construção. Ver Assumption Lock.
  • O rename é irreversível na prática — 11 diretórios, 11 plugin.json, marketplace.json e 46 invocações cruzadas. Uma referência órfã quebra a cadeia de dependência entre plugins em runtime, não em build (não há CI nem teste neste repo). Mitigação: varredura de órfãos como AC explícito.
  • O mecanismo documentado não é o mecanismo em uso — medido em 2026-09-13, o caminho de instalação descrito no README nunca foi exercitado de ponta a ponta — nem na máquina do autor (evidência em portabilidade). Mitigação: a US-005 verifica esse caminho especificamente.
  • Dependência externa do polyagent-mcp — vive fora deste repo e é pré-requisito de tudo. O projeto não controla sua instalação, só pode diagnosticá-la. E o contrato se move: em 2026-09-14 o bridge renomeou de cursor-mcp-bridge para polyagent-mcp (v0.5.0) e trocou todo o prefixo de env var CURSOR_* → POLYAGENT_*. O repo ficou com 47 ocorrências do nome antigo, em 30 linhas de 8 arquivos. Mitigação: a feature 2 alinha as referências; o diagnóstico da US-005 nomeia a versão esperada do bridge em vez de assumir.
  • Ausência de rede de segurança — o repo não tem build, test, lint nem CI. Qualquer edição em massa (o rename, sobretudo) é validada por inspeção, não por suíte.

Architecture & Diagrams

A arquitetura de 3 camadas (motor codex-image → genéricos → especialistas) e a família game dev (base pai codex-sprite + especialistas de estilo) permanecem como estão. Este PRD muda o que o motor sabe (feature 1), o que o projeto verifica sobre o ambiente (feature 2) e como tudo se chama (feature 3) — nenhuma das três reorganiza as camadas. Sem diagramas nesta versão: a mudança é de contrato e nomenclatura, não de topologia.

Só Linux será validado de fato. Se quebrar em qualquer um dos dois, dispara um update deste PRD — não um remendo silencioso.
i
ASSUMPTION: o projeto ainda não tem base de usuários externa, então o rename total sem alias de compatibilidade custa barato agora. Decisão explícita do usuário em 2026-09-13.
i
DECISÃO — cap de volume aceito com justificativa. As três features ficam em 125, 151 e 116 lines-equivalent, acima do cap de 60 do tier full. Aceito deliberadamente pelo usuário em 2026-09-14: o excesso é evidência medida — o critério testável de disponibilidade de motor, a verificação de colisão dos sete nomes candidatos e os 58 critérios de aceitação — não prosa. Podar até o cap removeria justamente as âncoras arquivo:linha que tornam os ACs verificáveis. Reavaliar se uma feature crescer com conteúdo que não seja evidência.

Global Open Questions

  • answered Quais motores entram? — Codex (gpt-image-2) e Grok (grok-4.5-build), os dois que o usuário já tem instalados. Terceiro motor é Non-Goal.
  • answered Quais sistemas operacionais? — Linux, macOS e Windows. Linux validado empiricamente; os outros dois por construção (ver Assumption Lock).
  • answered O rename mantém compatibilidade com os IDs antigos? — Não. Rename total, sem alias, com CHANGELOG avisando.
  • answered Prompt-only é só fallback de falha? — Não. É opção deliberada do usuário, disponível mesmo com motor instalado e funcionando.
  • answered Motor preferido ausente: troca sozinho ou pergunta? — Pergunta e espera confirmação; a qualidade do asset muda, então a decisão é do usuário. Prompt-only é pedido por engine: prompt, opção válida mesmo com motor disponível.
  • PO Qual o nome novo? — critérios fixados nesta versão (não amarrar a fornecedor, achável, disponível no GitHub); shortlist e verificação de disponibilidade são entregáveis da US-011, escolha final do usuário.
  • answered Como detectar que um motor está disponível sem pagar o custo de uma geração de teste? — binário resolvível + diretório de credencial (~/.codex/auth.json, ~/.grok), sem rede. Detalhe em multi-engine.
  • parked Como distribuir além do git clone (npm, registry próprio)? — Non-Goal desta versão; o marketplace declarativo já é o canal de instalação. Decisão tática: README documenta só clone + /plugin marketplace add.
  • parked Vale adicionar CI mínimo (validar JSON dos plugins, checar referências cruzadas órfãs)? — fora do escopo declarado, mas o rename aumenta o valor disso. Decisão tática: a varredura de órfãos da US-012 roda manual nesta versão; CI fica como próximo passo registrado.

Verification

Aceitação end-to-end do épico: numa máquina Linux limpa (container ou VM sem nada do ambiente do autor), git clone do repo, seguir o README do zero, rodar o diagnóstico da US-005 e confirmar que ele lista corretamente o que está presente e ausente; então gerar um sprite (esperado: Grok) e um retrato (esperado: Codex) confirmando que a skill informa qual motor usou; desinstalar um dos motores e repetir, confirmando que a skill pede confirmação antes de trocar em vez de trocar sozinha; desinstalar os dois e confirmar que o modo prompt-only entrega o prompt pronto sem erro. Por fim, após o rename, varrer o repo por qualquer ocorrência do nome antigo e por invocação <plugin>:<skill> apontando para plugin inexistente — o resultado esperado é vazio nos dois casos.
